# Project registry access — 2026-11-13

This note records the Layer 4 project registry operations in the file store that only authenticated the caller, the fix the user approved (owner-only, members use explicit sharing), and one cross-account read found in the same class. It follows the maintenance fix in [CM-AUDIT-014](./2026-11-13-file-import-project-id.md). PostgreSQL was not changed or reviewed.

## Findings

### 1. Registry operations only authenticated the caller — medium, confidence high, fixed, independently accepted (file store)

Path (before the fix): `register_branch`, `branches`, `register_worktree`, `worktrees`, `project_entities`, `freshness_history` and `close_branch` in `crates/core/src/lib.rs` each read `let _account = authenticate_account(..)` and only checked that the project exists. `confirm_branch_merge` authenticated and checked the project and branch but not who owned either. `register_project_entity` used the lenient `require_project_owner`, which passes any account for a project with no owner record. A registered outsider, an invited member and a removed member who knew the project id could register a branch or worktree in the owner's project, list them, read entity keys and freshness history (memory ids, commits and reasons) and close a branch. The earlier probe (`/tmp/cm-maintenance-probe`) showed an outsider registering a branch that the owner then listed. Prerequisite: the project id, which is not guessable but is known to members and former members.

### 2. A merge confirmation could copy another account's memory — medium to high, confidence high, fixed, independently accepted (file store)

`confirm_branch_merge` looked the source memory up by id with no ownership check, unlike `promote_memory`. An account that registers its own project for the same repository and a branch with the name stored in the victim's memory context, and that knows the victim's memory id, received a project copy of the victim's memory: the returned `ProjectMergeResult` carried its full content. Reproduced on a copy of the tree with only the new guard removed (the outsider's merge returned the victim's private text). Memory ids are not secret (shared promotions carry `source_memory_id`).

## Fixed (2026-11-13, file store only)

The eight operations above (the seven registry operations, `confirm_branch_merge`, and `register_project_entity`) authenticate first and then call `require_owned_project`, the strict helper added for maintenance: the project must exist (`unknown project: <id>`) and have an owner record that is the caller, otherwise `account does not own the project`. Validation, state changes and results for the owner are unchanged. `confirm_branch_merge` also calls `reject_other_owner` on the source memory, the guard `promote_memory` uses, so a foreign id reads `unknown memory or event: <id>`. The lenient `require_project_owner` is not changed, and share, membership, team and promotion code is untouched. A worktree's `branch_id` was already scoped to its own project and is unchanged. The registry has no web caller; MCP `memory_project_freshness` becomes owner-only; the PostgreSQL routes call the storage crate, which is unchanged.

Tests, written first: core `project_registry_is_owner_only_for_reads_and_writes` (nine operations: a current member, a removed member and an outsider are refused with one error, bad token and missing project keep their errors, the file is byte-identical and the reopened registry unchanged, the owner reads and writes normally, a merge cannot copy another account's memory, a foreign branch id does not resolve, an ownerless project is refused until the owner registers the repository) and server `project_registry_is_owner_only_over_http` (an outsider's read and write are 401 with the ownership error, no registry content and an unchanged file; the owner is 200). They failed on a copy that simulates the old behaviour (the ownership check removed: the outsider's first operation succeeded, the HTTP outsider got 200 instead of 401), and the merge-source case failed on a copy with only that guard removed (the outsider received the victim's content). They pass on the tree. After: `cargo test -p cairn-core --lib` (56), `cargo test -p cairn-server --lib` (35), `cargo fmt --all -- --check`, `cargo clippy -p cairn-core -p cairn-storage -p cairn-server --all-targets -- -D warnings`, the document validator. Not run: PostgreSQL, smoke scripts, a live server.

Docs updated, all still `draft`: [project-layer4](../contracts/project-layer4.md) and [ADR 0008](../adr/0008-self-hosted-account-authentication.md). Independent re-check, 2026-11-13: ACCEPT for the file store, nine registry operations, with B1 and R1 closed (the reviewer re-read the merged-branch repeat path and re-ran an extended probe on synthetic state, plus focused tests; it did not rerun the full suites, fmt, clippy or the validator; the implementer's checks were core 58, fmt, clippy and the validator, and the server suite and PostgreSQL were not rerun). This accepts only those operations in the file store, not the registry as a whole, the project area or all security. Still open: PostgreSQL (`confirm_branch_merge` and the other registry paths are not reviewed by this note), old aliased branches (denied the read, not repaired), the first-registrar claim of an ownerless project, the lenient `require_project_owner` for ownerless projects in other functions (promote, verify, share, team), and the project-existence error difference.

B1, 2026-11-13 (independent review, then fix). The reviewer found that the existing-promotion lookup in `confirm_branch_merge` scanned every stored row for the project and `promoted_from`, so a stored foreign row naming the owner's unmerged source was returned as the merge result, the branch's `merge_memory_id` pointed at it, the owner's commit and freshness were written onto it, a project index entry and a freshness event named it, and the owner's real promotion could never be created. It needs only already stored data. Fix: the lookup uses `project_rows(project_id)` (rows the project owner owns, plus rows with no owner), the same as `promote_memory`; the rest of the merge is unchanged. New core test `stored_foreign_project_rows_do_not_alias_a_branch_merge` failed first on the unfixed tree (the merge returned `memory-foreign-merge`) and passes: the owner gets its own promotion, the branch points at it, the foreign row (content, commit, freshness, owner) is unchanged and still exported by its owner, no foreign freshness or entity entry appears, a repeated merge is idempotent, and an unowned local row naming another source is still the idempotent promotion. The existing registry test also asserts that a rejected foreign-source merge leaves the outsider's project empty and its branch active. Checks: `cargo test -p cairn-core --lib` (57), fmt, clippy (core, storage, server), the document validator; the server suite was not rerun (no server change), PostgreSQL not run. R1 (independent re-check of B1, then fix): the merged-branch idempotent path still looked the recorded `merge_memory_id` row up over every stored row, so a branch aliased to a foreign row by the old behavior returned that row to the owner on a repeat merge with the same commit (a read of old data; no post-fix call can create the state). Fix: that lookup also uses `project_rows(project_id)` and returns the row by value; if the referenced row is not an owner-visible row of this project, the call falls through to the existing `project branch is already merged` error. Nothing is rewritten, rebound or repaired: such an old branch is denied the read, and its aliased `merge_memory_id` stays as stored. New core test `merged_branch_aliased_to_a_foreign_row_is_not_returned` failed first on the unfixed tree (the foreign row was returned) and passes for a foreign-owned row and for a row of another project: the error is the existing text with no foreign payload, the file is byte-identical, the branch alias and the foreign row and its owner's export are unchanged, an outsider is still refused and a bad token fails on authentication; the existing merge test now also repeats the unowned local merge, which stays idempotent. After: `cargo test -p cairn-core --lib` (58), fmt, clippy (core, storage, server), the document validator; the server suite and PostgreSQL were not rerun. Independently accepted; old-data repair stays open.

## Limits and uncertainties

- An ownerless project is claimed by the first account that registers its repository. That is existing behavior and not proof of the original owner; nothing repairs it.
- Foreign and missing projects still return different texts (the sibling convention), so a registered account can still tell an existing project id from a missing one. No separate non-oracle policy was decided.
- A row owned by another account that already sits in a project (old data) is hidden from the owner views by CM-AUDIT-014; this note does not change that.
- PostgreSQL registry and merge paths were not reviewed.
